# ベンチ結果

Rails版、Go版、snails版の3つのAPIに、同じPostgreSQLの100万行を読ませて測った結果です。3者は同じBasic認証と回数制限を通り、同じJSONを返します。

## 測定環境

| 項目 | 値 |
|---|---|
| 日時 | 2026-11-27 14:50 JST |
| マシン | Apple Silicon Mac（arm64、12コア）、macOS（Darwin 27.2.0） |
| DB | PostgreSQL 16（colimaのDocker VM、8コア、`--shm-size=1g`） |
| データ | `orders`表 1,000,000行（`bench/db/seed.sql`） |
| 負荷 | k6 2.3.0、同時接続32、ウォームアップ10秒、計測30秒 |
| コミット | `46487ee` |

各実装の起動条件は次のとおりです。

- Rails Pumaのワーカーを12プロセス、各5スレッドで動かします。DB接続は合計60本です。
- Go 1プロセスで全コアを使います。DB接続は60本です。
- snails 1プロセスで、コアごとのOSワーカーを使います。DB接続は60本です。

3者は1つずつ動かし、同時には動かしません。シナリオごとにサーバーを起動し直し、実装を替えるときは60秒置きます。各シナリオの前にはロードアベレージが6以下に下がるまで待つ手順です。負荷ツールとサーバーとDBは同じMacで動くので、CPUを取り合います。

## シナリオ

- light 注文日を1日に絞り、先頭の50件を取ります。
- list 一覧の先頭200ページから50件ずつ取ります。
- deep 2,001〜20,000ページ目を、注文日の降順で50件ずつ取ります。
- tree 500件を顧客、商品、注文の3段のツリーにまとめて返します。
- filter 顧客名の部分一致、状態の一致、日付の範囲を組み合わせて絞り込みます。

どのシナリオもページの行に加えて条件に合う件数を`COUNT(*)`で数えます。PostgreSQLで1回ずつ測ると、全件の`COUNT(*)`は14.9ms、1日に絞った件数と50件の取得は合わせて約2.6msでした。

## 読み方

アプリケーション側の速さの差はlightで読みます。GoはRailsの1.56倍、snailsの1.79倍の件数をさばきました。snailsはRailsより13%少ない件数でしたが、p99は26.8msでRailsの29.3msより短くなりました。

list、filter、deep、treeの4つはDBが上限です。listの全件`COUNT(*)`は1回で14.9msかかり、並列ワーカーで複数コアを使います。234 req/sではVMの8コアをほぼ使い切るので、GoとRailsの差はlistで3%、filterで3%に縮みました。この4つの数字はDBが詰まったときの各実装のふるまいとして読みます。

DBが上限のシナリオでもsnailsはlistでGoより18%、filterで24%少ない件数でした。treeではsnailsのp99が8,785.7msで、GoとRailsの約2.0倍です。

メモリはGoが27〜35MiB、snailsが87〜361MiBです。Railsは12プロセスで1,312〜1,448MiBを使います。
